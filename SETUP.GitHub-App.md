# GitHub App Setup for Omnia Reader

Omnia Reader uses a GitHub App, rather than an OAuth App, for Git and Git LFS
synchronization. The browser communicates only with the same-origin sync
gateway. GitHub credentials, user tokens, installation tokens, and reusable
sessions must remain in the gateway and must never be stored in Angular,
synchronization documents, URLs, or logs.

## 1. Register the GitHub App

Open GitHub and go to **Settings → Developer settings → GitHub Apps → New
GitHub App**.

For local development, configure:

| Setting                                           | Value                                                 |
| ------------------------------------------------- | ----------------------------------------------------- |
| GitHub App name                                   | `Omnia Reader Dev`, or another unique name            |
| Homepage URL                                      | `http://localhost:4300`                               |
| User authorization callback URL                   | `http://localhost:4300/api/sync/github/auth/callback` |
| Setup URL                                         | `http://localhost:4300/settings/sync`                 |
| Redirect on update                                | Enabled                                               |
| Request user authorization (OAuth) during install | Disabled                                              |
| Expire user authorization tokens                  | Enabled                                               |
| Webhooks                                          | Inactive unless a public development tunnel is used   |

Keep **Request user authorization (OAuth) during installation** disabled.
Omnia Reader starts a separate, state-bound, S256 PKCE-protected authorization
flow after installation. Combining installation and authorization callbacks
would bypass the authorization state and one-time verifier generated by the
sync gateway.

For **Where can this GitHub App be installed?**, choose:

- **Only on this account** for a private or personal deployment.
- **Any account** when other users or organizations should be able to install
  the App.

GitHub documents these fields in
[Registering a GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)
and explains the separate authorization callback in
[About the user authorization callback URL](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-user-authorization-callback-url).

## 2. Grant repository permissions

Under **Repository permissions**, grant:

- **Contents: Read and write**. This is required for synchronization,
  manifests, `.gitattributes`, and Git LFS pointers.
- **Administration: Read and write** only if Omnia Reader should create a
  private synchronization repository on the user's behalf.

There is no selectable event subscription to add for user authorization
revocation. When webhooks are active, GitHub sends the
`github_app_authorization` event so Omnia Reader can invalidate every local
session for the revoked user immediately. A loopback-only development gateway
cannot receive that event, so local development may leave webhooks inactive
and still detects revocation on the next definitive GitHub `401`.

If permissions are changed after users have installed the App, the existing
installations must approve the new permissions.

## 3. Create credentials and install the App

From the GitHub App's **General** page:

1. Record the numeric **App ID**.
2. Record the **Client ID**.
3. Generate a **client secret**.
4. Generate and download a **private key**.
5. Install the App on the intended user or organization account.
6. Grant access to either:
   - **All repositories** for the simplest repository onboarding; or
   - **Only select repositories** for least privilege.

The public installation URL is:

```text
https://github.com/apps/<app-slug>/installations/new
```

Store the client secret and private key in the gateway's secret storage. Do not
commit them or expose them to the browser.

## 4. Configure the local sync gateway

Create the local environment file:

```sh
cp apps/sync-gateway/.env.local.example apps/sync-gateway/.env.local
```

Generate a session-encryption key:

```sh
openssl rand -base64 32
```

Fill `apps/sync-gateway/.env.local`:

```dotenv
OMNIA_GITHUB_APP_ID=<numeric-app-id>
OMNIA_GITHUB_CLIENT_ID=<client-id>
OMNIA_GITHUB_CLIENT_SECRET=<client-secret>
OMNIA_GITHUB_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\n<key-body>\n-----END RSA PRIVATE KEY-----"
OMNIA_GITHUB_CALLBACK_URL=http://localhost:4300/api/sync/github/auth/callback
OMNIA_GITHUB_INSTALLATION_URL=https://github.com/apps/<app-slug>/installations/new
OMNIA_SYNC_SESSION_KEY=<output-from-openssl>
OMNIA_SYNC_SESSION_DIRECTORY=apps/sync-gateway/.session-data
```

The private key may use literal `\n` sequences. The session key must be the
Base64 encoding of exactly 32 random bytes. The session directory keeps the
encrypted connection across local gateway restarts. Never commit `.env.local`.
Do not set `OMNIA_GITHUB_WEBHOOK_SECRET` unless GitHub can reach the local
gateway through a trusted HTTPS tunnel.

The gateway fails closed if only part of the GitHub configuration is present.
Without GitHub credentials, its session endpoint reports the provider as
unconfigured instead of attempting authorization.

## 5. Start and verify the integration

Use the repository-defined Node version and locked dependencies:

```sh
nvm use
npm ci
npm run start:full
```

`npm run start:full` starts both the Angular application and the sync gateway.
The reader is available at <http://localhost:4300>, and the Angular development
server proxies `/api/sync` to the gateway on `127.0.0.1:3333`.

Open <http://localhost:4300/settings/sync>, then:

1. Select **Git + LFS**.
2. Use **Install GitHub App**.
3. Complete or update the GitHub App installation.
4. Return to Omnia Reader and use **Connect GitHub**.
5. Select an accessible repository or create a private repository.
6. Run synchronization.

An all-repositories installation can immediately discover repositories created
through Omnia Reader. With a selected-repositories installation, grant the
newly created repository to the App before refreshing the repository list.

Ordinary `npm start` intentionally starts the local-only reader without remote
synchronization. Use `npm run start:full` for GitHub integration.

## Production configuration

Use a public HTTPS reader origin for production. For example:

| Setting                         | Value                                                   |
| ------------------------------- | ------------------------------------------------------- |
| Homepage URL                    | `https://reader.example`                                |
| User authorization callback URL | `https://reader.example/api/sync/github/auth/callback`  |
| Setup URL                       | `https://reader.example/settings/sync`                  |
| Webhook URL                     | `https://reader.example/api/sync/github/webhook`        |
| Webhook secret                  | Independent random secret generated for this deployment |
| Webhooks                        | Active                                                  |

Configure the gateway with the same callback URL:

```dotenv
OMNIA_GITHUB_CALLBACK_URL=https://reader.example/api/sync/github/auth/callback
OMNIA_GITHUB_INSTALLATION_URL=https://github.com/apps/<app-slug>/installations/new
OMNIA_GITHUB_WEBHOOK_SECRET=<output-from-an-independent-openssl-rand-base64-32>
```

Generate the webhook secret independently with `openssl rand -base64 32`, put
the same value in the GitHub App webhook settings and the gateway secret
manager, and never reuse the client secret or session-encryption key.

The public `/api/sync` route must reach `apps/sync-gateway`. The callback URL
must use HTTPS except for `localhost` or `127.0.0.1`.

Use a secret manager for the App private key, client secret, and session key.
For localhost or a single gateway process, set
`OMNIA_SYNC_SESSION_DIRECTORY=apps/sync-gateway/.session-data` so the encrypted
GitHub connection survives gateway restarts. Use the documented Redis session
store when multiple gateway replicas serve the same origin or when GitHub
webhooks are enabled. Separate GitHub Apps for development and production are
recommended so that callbacks, keys, installations, and permissions remain
isolated.

## Security and operational notes

- GitHub credentials and tokens belong only in `apps/sync-gateway`.
- The gateway stores provider tokens in encrypted, server-side sessions and
  exposes only an HttpOnly session cookie to the browser.
- The production webhook validates the exact raw body with
  `X-Hub-Signature-256`, deduplicates `X-GitHub-Delivery`, and invalidates all
  sessions for the revoked GitHub user. Multi-replica deployments must share
  the documented Redis revocation store.
- Installation tokens are scoped to the selected repository and
  `contents: write`.
- Git LFS storage and bandwidth limits still apply. The gateway must report
  quota failures and must not fall back to storing publications as ordinary
  Git blobs.
- Live credentialed GitHub and Git LFS verification remains a separate release
  gate from unit tests.

For the complete gateway contract, including Redis key rotation and provider
security requirements, see
[`docs/sync-gateway-api.md`](docs/sync-gateway-api.md).
